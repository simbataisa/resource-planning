Backend and frontend · Development Engineering

Component Isolation Testing

The master design for testing one component in isolation, whether a Spring Boot service or an Angular or React web app, both on a developer laptop and in every Jenkins pipeline run. The backend uses Spring Boot test slices and Testcontainers on Rancher Desktop, Podman or the Jenkins agent; the frontend uses Testing Library, MSW and Playwright against the backend's contract stubs. All images and packages come from Nexus. Each branch gets its own private infrastructure, so several development streams can build and test in parallel without queuing for a shared SIT environment.

Based on Integration Testing Recommendations for Spring Boot Services Revision Oct 2026 Audience Development Engineers, Tech Leads, DevOps
Run it for real

Anything you own or can run in a container: your beans, the Spring context, PostgreSQL, Kafka, Redis, LocalStack.

Stub at the HTTP boundary

Anything another team or vendor owns. Use WireMock or contract stubs. Never use a Mockito mock of the client.

Mockito for unit tests

In L1 unit tests, mock collaborators freely to prove a class's logic. Above L1, mock only the edge of a slice, or a failure that is hard to cause for real.

Speed

  • Feedback in minutes. Integration feedback comes from the laptop and the PR build, without waiting for a SIT deployment or another team's environment.
  • A fast suite. Shared containers, local reuse and one cached context run 200 integration tests in 1–2 minutes instead of 40 or more.
  • Parallel development streams. Every Jenkins run and every laptop gets its own containers and stubs, so feature branches, release fixes and other teams' work never queue for or break a shared SIT.

Correctness

  • Production engines. PostgreSQL, Kafka and Redis run for real, so mapping, transaction and serialisation defects fail before merge.
  • Failure paths on demand. Rollbacks, timeouts, 5xx errors and rejected requests can be reproduced at will, which shared SIT rarely allows.
  • Repeatable results. Synthetic data isolated per test and contract checks in the provider's build keep the suite stable and catch API drift early.

Test taxonomy

Five levels, one home for each assertion

Every test belongs to exactly one level. The level decides what you may mock, what infrastructure is available and how long the test may take. The L1 to L5 labels are used throughout the rest of this page. Each layer shows its share of the suite and its time budget per test. Click a layer for details.

L1 is gated by test strength, not only by coverage

PIT checks that unit tests fail when the code is wrong: at least 70% overall and 80% in service and domain packages. Constraint coverage checks that every Jakarta constraint on DTOs, entities and custom annotations has a negative test: 100%. Both have an interactive demo in the component isolation map: Mutation (PIT) and Bean Validation.

Do not jump straight to @SpringBootTest

A full context is the most expensive thing in a suite. If a slice can prove the assertion, use the slice. Keep @SpringBootTest for behaviour that spans layers: a transaction that must commit, an event that must be consumed, a cache filled by a real call path.

H2 is not a test database

H2 in PostgreSQL mode is a different engine with a different dialect, type coercion, locking, sequences and JSON support. A green H2 suite tells you nothing about PostgreSQL. Remove H2 from every module.

@MockitoBean costs a new context

Every distinct set of mocked beans creates a new application context. Stub at the transport boundary instead, so the whole suite shares one context.

L1 · Mutation (PIT) · unit test strength

Mutation testing with PIT: do the unit tests actually catch bugs?

Line coverage only shows that code ran. PIT changes the production code in small ways, such as flipping a condition, removing a call or returning null, and re-runs the unit tests against each change (a mutant). If a test fails, the mutant is killed. If every test still passes, it survived: a bug like that would reach production unnoticed. The mutation score is the share of mutants killed.

Read the survivors, not just the score

A surviving mutant is a precise statement about a missing assertion. The most common cause of a low score is a test that calls a method and asserts only that nothing was thrown. That raises line coverage and protects nothing.

Why the PIT ramp is slower

Mutation score is the hardest gate to move, because it means rewriting weak assertions rather than adding new test files. The two extra phases prevent teams from deleting tests to push the score up. Thresholds only ever go up. Legacy classes come up to the current threshold when they are touched.

L1 · Bean Validation · constraint coverage

DTOs, entities and custom annotations: every constraint needs a failing test

Jakarta Bean Validation is declarative. An annotation such as @NotNull is not a branch, so JaCoCo reports nothing and PIT has nothing to mutate. A missing negative test is invisible to both gates. That is why constraint coverage is its own gate: 100%, with no exceptions. Every constraint on a DTO, a JPA entity or a POJO, including your own custom annotations, needs at least one test that deliberately breaks it.

CreatePaymentRequestValidationTest.java · L1, no Spring
class CreatePaymentRequestValidationTest {
  private final Validator validator = Validation.buildDefaultValidatorFactory().getValidator();

  // 1. One valid baseline, reused by every negative test (synthetic values only)
  private CreatePaymentRequest validDto() {
    var dto = new CreatePaymentRequest();
    dto.setTitle("Invoice 1");
    dto.setAmount(new BigDecimal("10.00"));
    dto.setCurrency("USD");
    dto.setPayerEmail("payer@example.com");
    dto.setExpiresAt(LocalDateTime.now().plusDays(1));
    return dto;
  }

  // 2. Prove the baseline really is valid, or every negative test passes for the wrong reason
  @Test
  void validDto_hasNoViolations() {
    assertThat(validator.validate(validDto())).isEmpty();
  }

  // 3. One negative test per constraint, changing exactly one field
  @Test
  void invalid_title_NotBlank_fails() {
    var dto = validDto();
    dto.setTitle(" ");
    assertThat(validator.validate(dto)).anyMatch(v ->
        v.getPropertyPath().toString().equals("title")
        && v.getConstraintDescriptor().getAnnotation() instanceof NotBlank);
  }
}
  • Write the negative test in the same commit as the annotation. The gate then never fails for someone else, later.
  • Assert the field and the constraint type, not just "some violation". Otherwise a different broken rule can make the test pass.
  • Controller wiring (@Valid → 400 with the standard error body) is a separate gate, proven in the web slice.

@Target({ElementType.FIELD, ElementType.PARAMETER})

@Constraint(validatedBy = SupportedCurrencyValidator.class)   // meta-annotation: the gate finds it automatically

  Class<?>[] groups() default {};
  Class<? extends Payload>[] payload() default {};

public class SupportedCurrencyValidator implements ConstraintValidator<SupportedCurrency, String> {
  private static final Set<String> SUPPORTED = Set.of("USD", "VND", "SGD");

  @Override
  public boolean isValid(String value, ConstraintValidatorContext context) {
    return value == null || SUPPORTED.contains(value);           // null is @NotNull's job
  }
}

Custom annotations get two kinds of test

The validator class is ordinary code: unit-test its logic, and PIT mutates it like any other class. Each place the annotation is used is declarative: it needs its own invalid_…_fails test, which the coverage gate checks. Class-level constraints (for example @ValidPaymentWindow comparing two fields) follow the same rule, with the test named after the class.

ConstraintCoverageGateTest.java · fails the build when a constraint has no negative test
class ConstraintCoverageGateTest {
  private static final List<String> MODEL_PACKAGES = List.of("com.ahss.dto", "com.ahss.entity", "com.ahss.event");

  @Test
  void everyConstraintHasANegativeTest() {
    var testNames = methodNamesOfClassesEndingWith("ValidationTest", "com.ahss");
    var missing = new ArrayList<String>();

    for (var type : classesIn(MODEL_PACKAGES)) {
      for (var field : type.getDeclaredFields()) {
        for (var annotation : field.getAnnotations()) {
          var constraint = annotation.annotationType();
          if (constraint.isAnnotationPresent(Constraint.class)) {      // built-in and custom alike
            var expected = "invalid_" + field.getName() + "_" + constraint.getSimpleName() + "_fails";
            if (!testNames.contains(expected)) missing.add(type.getSimpleName() + "#" + expected);
          }
        }
      }
    }
    assertThat(missing).as("constraints without a negative test").isEmpty();
  }
  // classesIn / methodNamesOfClassesEndingWith: ClassPathScanningCandidateComponentProvider
  // with an always-true filter, from your shared test library.
}

The naming convention invalid_<fieldName>_<ConstraintName>_fails is what the gate matches on. It runs with the ordinary unit tests in the pre-push hook and in Jenkins stage 2, so there is no extra tool to install.

Layer recipes

One proven pattern per layer

Each recipe states what to prove, which level it belongs to and the smallest test that proves it. All data is synthetic.

Classes the recipes rely on

L3 recipes extend AbstractIntegrationTest. Slices import PostgresContainerConfig or RedisContainerConfig. Helpers such as tenant(…), payment(…), newPayment(…), fixtures and uniqueTenantId() come from TestData and PaymentFixtures. All of them are written out in full in Setup step 4 · Test foundation.

@WithSecurityContext(factory = WithTenantUserFactory.class)
public @interface WithTenantUser {
  String user() default "test-user-1";

class WithTenantUserFactory implements WithSecurityContextFactory<WithTenantUser> {
  @Override
  public SecurityContext createSecurityContext(WithTenantUser u) {
    Jwt jwt = Jwt.withTokenValue("test-token")
        .header("alg", "none")
        .subject(u.user())
        .claim("tenant_id", u.tenant())
        .build();
    var ctx = SecurityContextHolder.createEmptyContext();
    ctx.setAuthentication(new JwtAuthenticationToken(jwt, AuthorityUtils.createAuthorityList(u.authorities())));
    return ctx;
  }
}

@Component
@Order(SecurityProperties.DEFAULT_FILTER_ORDER + 1)   // runs after Spring Security, so the tenant is known
public class RateLimitFilter extends OncePerRequestFilter {
  private final RateLimitBuckets buckets;             // in memory in slices, Redis-backed everywhere else
  private final ObjectMapper json;

  RateLimitFilter(RateLimitBuckets buckets, ObjectMapper json) { this.buckets = buckets; this.json = json; }

  @Override
  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
      throws ServletException, IOException {
    var probe = buckets.forTenant(TenantContext.currentTenantId()).tryConsumeAndReturnRemaining(1);
    if (probe.isConsumed()) {
      res.setHeader("X-RateLimit-Remaining", Long.toString(probe.getRemainingTokens()));
      chain.doFilter(req, res);
      return;
    }
    long retryAfter = TimeUnit.NANOSECONDS.toSeconds(probe.getNanosToWaitForRefill()) + 1;
    res.setStatus(HttpStatus.TOO_MANY_REQUESTS.value());
    res.setHeader(HttpHeaders.RETRY_AFTER, Long.toString(retryAfter));
    res.setContentType(MediaType.APPLICATION_JSON_VALUE);
    json.writeValue(res.getOutputStream(), new ErrorBody("RATE_LIMITED", "Too many requests", null));
  }

  @Override
  protected boolean shouldNotFilter(HttpServletRequest req) {
    return req.getRequestURI().startsWith("/actuator");   // health checks are never limited
  }
}

Which one to use

Use the contract stub for the request and response shape the two teams agreed. Use hand-written WireMock stubs for behaviour a contract does not describe, such as a 5-second delay, a dropped connection or a retry sequence. Target architecture

What runs where on a developer laptop

The test JVM talks to a local container runtime over a Docker-compatible socket. That runtime pulls every image from Nexus, never straight from Docker Hub. Spring Boot reads the mapped ports through @ServiceConnection, so no test hard-codes a URL.

Docker API / container Image pull from Nexus Mapped port → Spring

Docker API socket

Rancher Desktop must use the moby (dockerd) engine. containerd has no Docker-compatible API.

Mapped ports

On macOS, container ports are published on the VM IP. TESTCONTAINERS_HOST_OVERRIDE points Spring at it.

Images

One prefix rewrites every Docker Hub name to Nexus. Internal images use their full Nexus name.

Setup guide

Nexus checklist for DevOps

  • docker-proxy pointing at Docker Hub, with an authenticated upstream account to avoid rate limits.
  • docker-hosted for internal images, such as stub servers and base images. CI has push rights.
  • docker-group combining both, published on one HTTPS endpoint (for example port 8443).
  • Docker Bearer Token Realm turned on under Security → Realms. Developers get a pull-only role.
  • maven-public group for Gradle and Maven dependencies.
  • For air-gapped agents, pre-seed every image in the table above, including testcontainers/ryuk and alpine.

Use names like postgres:16-alpine in code. A name with an explicit docker.io/ host is skipped by the prefix and goes straight to Docker Hub.

Tech lead · once per service, then moved to a shared test library

These are the classes every example on this page relies on. Each one is written out in full in the tabs below.

    Inside the integration stage

    The build gets its own private copy of every dependency. Real engines run in containers on the agent, and other teams' APIs are WireMock stubs inside the test JVM. Each test then exercises its layers end to end against that private infrastructure, with no shared SIT and no shared database.

    What happens in the stage

    1. Start Ryuk for this build's session.
    2. Pull images from Nexus. Images already in the agent's local image cache start immediately.
    3. Start PostgreSQL, Kafka, Redis and LocalStack on random ports and wait until each is healthy.
    4. Build one Spring context. @ServiceConnection wires each mapped port and Flyway migrates the schema.
    5. Run every L3 test class against that context, with a unique tenant per test and WireMock reset before each test.
    6. Publish results. JUnit XML goes to Jenkins and reports are archived; container logs are attached on failure.
    7. Clean up. Ryuk removes the containers, even if the build was aborted.

    Isolation guarantees

    • Per build: fresh containers, no reuse and no shared state with any other build or environment.
    • Per agent: random host ports and Ryuk session labels let concurrent builds share an agent safely.
    • Per test: a unique tenant ID scopes all data, so tests can run in parallel and in any order.
    • Per dependency: other teams' APIs are stubs you control, including their failure modes.

    Many development streams, no shared environment

    Use a multibranch pipeline. Every branch and pull request then runs the full L1 to L4 suite against its own private containers and stubs.     Observability

    Distributed tracing with OpenTelemetry

    One trace ID follows each request through the filters, the service, PostgreSQL, Core Banking and Kafka. That holds on a laptop, in every Jenkins run and in shared environments. A failing test or a slow request points straight at the span that broke, so you no longer have to search logs across services.

    Faster debugging

    A failed test or a 5xx response shows exactly which span failed and how long each step took. You find the cause in minutes instead of reproducing it in SIT.

    End-to-end traceability

    The trace ID is in every log line, every error body, every outbound HTTP call (traceparent) and every Kafka message header, so asynchronous hops stay connected.

    Performance insight early

    Span timings expose N+1 queries, slow upstream calls and retry storms during development, long before a load test finds them.

    Stubs are not test data for people

    Everything served by MSW and Stub Runner is synthetic by construction. Never record handlers from a real environment, and never paste production payloads into a handler file.

    One contract, both sides

    The backend verifies the contract in its build and publishes the stubs. The frontend tests against those stubs and generates its types from the same OpenAPI. A field renamed on the server fails the provider build first, and if it ever got through, the frontend's contract tests fail next. Neither team waits for SIT to find out.

    Rule of thumb

    If the assertion is about a value, it is Tier 1. If it is about what the control shows or emits after an event, it is Tier 2. Only if it needs a layout engine, the OS, a second screen or a second browser engine is it Tier 3. A validation that is tested only in Playwright is a smell: it means the rule is buried in a template and cannot be unit-tested, so move it into the schema or the component.

    UI framework components

    Angular Material, PrimeNG, MUI and Ant Design already test their own widgets. Your Tier 2 test proves your wrapper: options come from the schema enum, the required message is yours, the value emitted is the model type (string amount, ISO date, true/false). Where a native input would be needed for the browser to validate (type=number), wrap it or replace it, so the rule is in code you can unit-test, and keep one Playwright test per widget family for keyboard and overlay behaviour.

    test/field-cases.ts · value factories: one line per field in a test
    import { MATRIX, Case } from './field-matrix';
import { fieldSpec } from './openapi-fields';          // generated: name → { type, min, max, enum, pattern, … }

export type FieldCase = [name: string, value: unknown, expectValid: boolean];

const INJECT  = [`' OR 1=1 --`, '<script>alert(1)</script>', '{{7*7}}', '${7*7}', '../../etc/passwd'];
const SPECIAL = ['!@#$%^&*()', '"quoted"', 'back\\slash', 'tab\there'];
const UNICODE = ['Nguyễn Văn Ánh', '日本語', '🙂', '​zero​width', '‮right-to-left'];

export function fieldCases(field: string): FieldCase[] {
  const s = fieldSpec(field), out: FieldCase[] = [];
  for (const c of MATRIX[s.type]) out.push(...casesFor(c, s));
  return out;
}

function casesFor(c: Case, s: FieldSpec): FieldCase[] {
  switch (c) {
    case 'null':    return [[`${s.name}_null`, null, false]];
    case 'empty':   return [[`${s.name}_empty`, '', false]];
    case 'space':   return [[`${s.name}_space`, '   ', false]];
    case 'min':     return [[`${s.name}_min_below`, below(s.min, s), false], [`${s.name}_min_at`, s.min, true]];
    case 'max':     return [[`${s.name}_max_above`, above(s.max, s), false], [`${s.name}_max_at`, s.max, true]];
    case 'bound':   return [[`${s.name}_bound_min`, s.min, true], [`${s.name}_bound_min1`, step(s.min, +1, s), true],
                            [`${s.name}_bound_max1`, step(s.max, -1, s), true], [`${s.name}_bound_max`, s.max, true]];
    case 'type':    return [[`${s.name}_type`, wrongType(s), false]];
    case 'format':  return badFormats(s).map((v, i) => [`${s.name}_format_${i+1}`, v, false]);   // 3 per type
    case 'enum':    return [[`${s.name}_enum_outside`, 'XXX', false], [`${s.name}_enum_case`, s.enum![0].toLowerCase(), false]];
    case 'dup':     return [[`${s.name}_dup`, { duplicateOf: 'existing' }, false]];   // handled by the API/MSW, see tab 5
    case 'special': return [[`${s.name}_special`, SPECIAL[0], s.allowSpecial ?? false]];
    case 'unicode': return [[`${s.name}_unicode`, UNICODE[0], s.allowUnicode ?? true]];  // names must accept Vietnamese
    case 'inject':  return INJECT.slice(0, 1).map(v => [`${s.name}_inject`, v, false]);
  }
}
// badFormats('decimal') → ['10.001', '10,00', '1e3'];  badFormats('email') → ['payer.example.com', 'a@b', 'a@@b.com'];
// badFormats('datetime') → ['2026-13-01T00:00:00Z', '01/02/2026', 'yesterday'];  wrongType('integer') → '12abc'
// All sample values are synthetic.

    Unicode and Special are not always "invalid"

    A Vietnamese name must accept diacritics, and a password must accept special characters. The matrix says the case must exist; the schema says whether the value is accepted or rejected. That is why each case carries expectValid, and why a rejected Vietnamese name is a bug the gate makes visible.

    Is the matrix exhaustive? No, and it should not try to be

    It is the per-field syntactic floor: the cases every field of a type must have before review. Three kinds of defect sit outside it and need their own layer, otherwise teams assume "matrix green" means "validation done".

    • Cases the 13 columns do not name. Worth adding as columns 14–19 in field-matrix.ts (the gate picks them up automatically): Whitespace inside ("10 .00", "079 123"), Case (usd, Payer@Example.COM), Sign and zero (-10.00, +10, -0, leading zeros 007), Precision (1e3, NaN, Infinity, 9007199254740993 beyond 253, rounding half-up vs banker's), Length in graphemes vs bytes (an emoji is 1 character, 2 UTF-16 units, 4 bytes; maxLength: 140 means which?), Null vs missing vs empty ({"x": null}, key absent, "", [] are four different inputs to an API).
    • Field types the 21 rows do not cover. Lists and arrays (min/max items, duplicates inside the list, null elements), nested objects, multi-select, OTP, masked card number, time-only, duration, country and language codes, rich text / HTML, JSON blobs, signed amounts (refunds). Add a row per type with its factories; the self-test fails until the factories exist.
    • Rules that are not per-field at all. Cross-field (startDate < endDate, sum of lines equals total, "required if" another field is set), state-dependent (a cancelled payment cannot be approved), and semantic (limit per tenant, KYC level, balance). These belong to a cross-field layer (schema refine / Angular group validators, Tier 1) and a business-rule layer proven against the API (L3 and contract), never to the matrix.
    • Transport and structure. Unknown extra properties (reject or ignore, but decide), wrong Content-Type, oversized payload, duplicate JSON keys, numbers sent as strings and the reverse, arrays where an object is expected. Cover with one schema-level test per request type and with the response check in tab 5.

    What keeps the matrix honest is the pair around it: the gate proves nothing was skipped from the floor, and property-based fuzzing looks for what the floor did not name. When fuzzing finds a new class of failure, promote it to a column, so the next field gets it for free.

    • Per-field overrides. A field can add or drop cases in the schema (x-cases-add: [dup], x-cases-skip: [unicode] with a reason). The gate reads the override, so the exception is visible in the contract, not hidden in a test.
    • Locale. Decimal comma, VND without decimals, and dd/MM/yyyy display are UI formatting, not model format. The model is always "10.00" and ISO-8601; locale cases live in the Tier 2 control tests, not in the matrix.
    • Normalisation. Add NFC/NFD pairs and zero-width characters to Unicode; they are the usual cause of "name does not match" defects in identity flows.
    • Share the corpus. Export corpus.json from the shared test library so the backend's constraint tests and WireMock stubs use identical values. A value the UI rejects and the API accepts (or the reverse) then shows up as a failing test on one side.

// Tier 1 expected names: field_<name>_<case>[_<variant>], exactly what fieldCases() generates
function tier1Names(f: { name: string; type: FieldType }): string[] {
  return MATRIX[f.type].flatMap(c => CASE_SIZE[c] === 1 ? [`field_${f.name}_${c}`] : variantsOf(f.name, c));
}
// Tier 2 expected: at least one ui_<name>_* test, and ui_<name>_dup when the field is x-unique
function tier2Missing(f: { name: string; unique?: boolean }, ran: Set<string>): string[] {
  const out: string[] = [];

  if (f.unique && !ran.has(`ui_${f.name}_dup`)) out.push('ui_dup (server 409 shown on the field)');
  return out;
}

    Troubleshooting

    Common failures on a laptop

    Could not find a valid Docker environmentboth

    Testcontainers cannot reach the daemon. Check that echo $DOCKER_HOST points to a socket that exists. On Rancher Desktop, the engine must be moby. On Podman, run podman machine start. An IDE launched from the Dock does not read ~/.zshrc. Add the same variables to the IDE's test run configuration, or start the IDE from a terminal.

    client version 1.32 is too oldboth

    Older Testcontainers clients default to Docker API 1.32, which current engines reject. Upgrade to the Testcontainers 2.x BOM shown in step 3.

    Connection refused on mapped portsRancher · macOS

    Ports are published on the VM IP, not on localhost. Make sure TESTCONTAINERS_HOST_OVERRIDE is set: rdctl info --field ip-address must return an address. Use the VZ VM type. QEMU needs administrative access to get a routable IP.

    Can not connect to Ryukboth

    Ryuk mounts the Docker socket from inside the VM. Set TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock. On rootless Podman, set TESTCONTAINERS_RYUK_DISABLED=true or switch the machine to rootful.

    401 Unauthorized or pull access denied from NexusNexus

    Testcontainers sends credentials from ~/.docker/config.json or DOCKER_AUTH_CONFIG. With Podman, log in with --authfile "$HOME/.docker/config.json". On the Nexus side, the Docker Bearer Token Realm must be on and your role must allow pulls from docker-group.

    x509: certificate signed by unknown authorityNexus

    The VM does not trust the corporate CA that signs the Nexus certificate. On Rancher Desktop for macOS, add the CA to the macOS keychain and restart Rancher Desktop so it copies the CA into the VM. On Podman, copy the CA into the machine and restart it:

    podman machine ssh "sudo mkdir -p /etc/containers/certs.d/nexus.example.internal:8443"
podman machine ssh "sudo tee /etc/containers/certs.d/nexus.example.internal:8443/ca.crt" < corp-root-ca.crt
podman machine stop && podman machine start

    Do not work around this with an insecure-registry setting.

    manifest unknown for an imageNexus

    The image is not in Nexus, or the name was rewritten wrongly. Check the prefix keeps its trailing slash. Names with an explicit docker.io/ are not prefixed. Air-gapped proxies need DevOps to pre-seed the image.

    New containers start on every runreuse

    Reuse needs three things: testcontainers.reuse.enable=true in ~/.testcontainers.properties (the classpath file is ignored for this setting), .withReuse(true) on the container, and an unchanged container definition. Any change to image, environment or command creates a new container.

    Podman asks which registry to use for a short namePodman

    Testcontainers cannot answer the prompt. With the Nexus prefix every name is fully qualified, so the prompt should not appear. If it does, set short-name-mode="permissive" in the machine's /etc/containers/registries.conf.

    LocalStack fails with an authentication errorLocalStack

    Since March 2026, current localstack/localstack releases need a LOCALSTACK_AUTH_TOKEN. Keep the pinned 3.8 tag mirrored in Nexus, or agree a licensed token with the platform owner before you upgrade.

    The suite builds many contextsspeed

    Turn on logging.level.org.springframework.test.context.cache=DEBUG and look for cache misses. Then remove the cause using the table in "Keeping the suite fast".
