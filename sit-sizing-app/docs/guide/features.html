Feature guide

How every feature of SIT Sizing works

SIT Sizing estimates the test cases, hours and FTE needed for system integration testing. Each section below explains one feature: what it is for, exactly what happens, who may use it, and an animation of the mechanism. Use the replay button on any animation to watch it again.

The life of an estimate

Projectteam and roles→ Estimateone release or change→ Draftedited live→ Version 1, 2, 3…immutable→ Submittedfor review→ Approvedby a QE Lead→ Actualsafter SIT→ Calibrated profilebetter next time

The loop closes: measured actuals feed a calibrated profile, which the next estimate starts from.

Basics

Sign-in and roles

Who you are comes from Keycloak, the app's own identity provider. What you may do in each project is stored in the app.

What happens

  1. Opening any page without a session sends you to the Keycloak sign-in page.
  2. You sign in with username and password (Admins also use an authenticator app).
  3. Keycloak sends you back with a one-time code; the app exchanges it for tokens on the server.
  4. The app keeps an encrypted session cookie and refreshes the tokens quietly in the background.
  5. Every request is checked against one permission table. The screen hides what you cannot do, but the server check is the real control.
  6. Signing out, or an admin ending your session in Keycloak, signs you out of the app at once (back-channel logout).

Basics

Projects and members

A project is a product or programme. It owns estimates and has members, each with one role.

What happens

  1. An Admin creates a project. Projects can later be archived, which hides them from lists and the portfolio.
  2. On the project page everyone can see who the members are.
  3. A QE Lead or Admin adds people by work email and gives each a role: Viewer, Estimator or QE Lead.
  4. A person must have signed in once before they can be added; the error names anyone who has not.
  5. A project must always keep at least one QE Lead. The browser and the server both check this.
  6. Every membership change is written to the audit log.

Estimating

The calculation engine

One engine, written in TypeScript, computes every number. It is a faithful port of the original HTML prototype and is checked against it on 5,000 random cases. It runs in your browser for live results, and again on the server, whose numbers are the ones stored.

From scope to FTE

  1. Drivers. Your scope becomes counts: APIs, screens, integrations, rules, journeys, batch jobs, events, workflows, fields, data feeds, AI intents, performance scenarios, each split into Simple, Medium and Complex.
  2. Test cases. Each driver turns into test cases by group (functional, validation, mapping, mobile, data, AI, performance and so on), with uplifts for critical rules, variants, languages and channels. Cases are rounded per group and band.
  3. Minutes. Each case gets design minutes and execution minutes. Execution defaults to 10, 20 and 40 minutes for Simple, Medium and Complex, multiplied by cycles, regression and a 20% retest rate.
  4. Hours. Minutes become hours, plus a 15% overhead on every group.
  5. FTE. Hours are divided by what one person delivers in the test window: weeks × 5 days × 6 productive hours × the team's blended capacity.
  6. Range. FTE is shown with a low–high range: ±40% in rough mode, ±15% in detailed mode.

All defaults above are among the 142 assumption values. A profile can change them (see Assumption profiles).

The pipeline

Estimating

Rough and detailed modes

Every estimate is computed both ways at once. Rough mode works from a features list early on; detailed mode works from real counts once the FSD exists. The gap between them shows where the early estimate was off.

What happens

  1. Rough scope tab. You list features, each with a type (application, data, AI), a size (S, M, L, XL), a complexity and a quantity. Each size stands for typical counts; for example an L application feature counts as 4 screens, 8 APIs and 30 fields.
  2. Detailed scope tab. Nine collapsible sections take exact counts by complexity: application drivers, fields and payloads, roles and rules, data platform, AI product, performance and more.
  3. Both modes run on every change. Results show summary cards for each, side by side.
  4. The gap table lists every group with rough and detailed hours, and highlights the group with the biggest difference.
  5. The sensitivity chart swings each of 42 key inputs and assumptions up and down and shows which move FTE most.
  6. The calendar check warns when the work does not fit the test window.

Estimating

Shift-left credit

When earlier testing is proven (unit test coverage, contract tests, automated validation), SIT does not need to repeat it in full. The Shift-left evidence tab records that evidence and the engine gives credit for it.

What happens

  1. You enter coverage percentages and yes/no evidence gates, for example code coverage or contract test coverage.
  2. Each coverage value is turned into one of three credit states.
  3. 100% or more: SIT keeps only a sample of those cases.
  4. 50–99%: part of the work comes back to SIT.
  5. Below 50%: SIT tests that area in full.
  6. The shift-left scenarios panel shows how FTE would change if more gates were met, so the team sees what earlier testing is worth.

Estimating

Editor, autosave and the edit lock

Each estimate has one draft. Only one person edits it at a time, and every change is saved automatically.

What happens

  1. The editor has the prototype's five tabs: Rough scope, Detailed scope, Window/team/environment, Shift-left evidence and Assumptions.
  2. Opening the draft for editing takes a lock for 15 minutes, renewed by a heartbeat while you work. Others see "being edited by …" and a read-only view.
  3. Every keystroke recomputes the results in your browser.
  4. 1.5 seconds after you stop typing, the draft is autosaved. The server recomputes and stores the authoritative result.
  5. Each save carries a row version. If the draft changed underneath you (the lock was lost), the save is refused, the editor reloads, and your unsaved values are kept in a side panel.
  6. A QE Lead can take over a lock, for example when someone left the editor open.

Review

Versions and approval

Saving the draft creates a numbered version that never changes. A version is reviewed through a short workflow, and nobody approves their own work.

What happens

  1. Save version. An Estimator saves the draft as version 1, 2, 3… with a note. It stores the inputs, assumptions and the result, stamped with the engine version.
  2. Submit. An Estimator submits a saved version. Only one version per estimate can be under review at a time. The project's QE Leads are notified.
  3. Approve or return. A QE Lead approves it, or returns it to Saved with a note. Author and submitter are notified.
  4. Segregation of duties. Whoever wrote or submitted the version cannot approve it, whatever their role, Admins included. The Approve button is disabled and says why.
  5. Approving a version marks the previously approved one Superseded.
  6. Every step is one database transaction with an audit event; two people clicking at once cannot both win.

States of a version

SAVED→ SUBMITTED→ APPROVED→ SUPERSEDED

Blocked: the QE Lead who submitted version 3 cannot approve it. Another QE Lead must.
Review

Compare and restore

See exactly what changed between any two versions, and start again from an old one without losing anything.

What happens

  1. Pick any two versions of an estimate.
  2. The comparison shows both summaries, rough and detailed figures, cases and hours per group, and a list of every input and assumption that changed (up to 500 entries).
  3. Figures come from what each version stored, so a comparison never recomputes and always shows what was saved.
  4. Restore as new draft starts a draft from an old version. The old version itself never changes.

Review

Assumption profiles and calibration

The engine uses 142 assumption values, such as minutes per case or retest rate. A profile is a named set of them, managed centrally, so teams start from measured values instead of guesses.

What happens

  1. Profiles are global (managed by Admins) or per project (managed by that project's QE Leads).
  2. A profile moves Draft → Published → Retired. Only drafts can be edited. To change a published profile, clone it into a new draft.
  3. A value is calibrated when it differs from the engine default. A calibrated value records its source (for example a SIT cycle) and the date it was measured.
  4. Creating an estimate, you pick a published profile. With none chosen, the oldest published global profile is used.
  5. On an open draft, Apply profile replaces all 142 values and recomputes, after you confirm.
  6. Values are copied into the estimate, never linked, so retiring a profile changes nothing already saved. The last published global profile cannot be retired.

After SIT

Actuals and variance

After a SIT cycle, record what really happened against the approved estimate, and see how far off it was.

What happens

  1. On an approved version (or one superseded after the cycle ran), an Estimator records a cycle: test cases executed and total SIT hours are required; execution hours, design hours, retests and productive hours per day are optional.
  2. Variance = actual − estimate, per cycle, with a percentage of the estimate. It is computed when shown, never stored, and uses the detailed result.
  3. Four measured rates are shown next to the assumption each one informs: execution minutes per case, design minutes per case, retest rate and productive hours per day.
  4. A QE Lead decides which rates to adopt, puts them in a profile with the cycle as the source, and publishes it. People decide; the app does not change profiles by itself.

After SIT

Portfolio

Totals across projects for quarterly business reviews, taken from what was approved.

What happens

  1. One row per estimate: its approved version by default, or its newest saved version to show work in progress. Drafts and archived items are left out.
  2. Figures come from each version's stored result; nothing is recomputed.
  3. Totals are plain sums with subtotals per project. Ranges add low to low and high to high, which gives the widest honest range; the page says so.
  4. Each row shows how many of its 142 assumptions are uncalibrated.
  5. QE Leads see the projects they lead; Admins see all. A CSV export in English or Vietnamese goes into the QBR pack.

After SIT

Export

Take a version out of the app as an Excel workbook, CSV, JSON or a text summary.

What happens

  1. Anyone who can read the estimate can export it. Each download is audited.
  2. The server recomputes from the stored inputs and assumptions and builds plain tables, then renders them as Excel or CSV, in English or Vietnamese.
  3. The links wait for autosave first, so the file matches the screen.
  4. Excel totals are live SUM formulas whose saved results equal the engine totals, and numbers are unrounded, formatted by Excel.
  5. CSV is protected against formula injection: text starting with = + - @ gets an apostrophe.
  6. JSON export and import stay compatible with the original HTML tool.

After SIT

Notifications

People hear about reviews and new profiles in the app and by email, and no notice is ever lost or sent twice.

What happens

  1. Submitting, approving, returning or publishing a profile writes notices in the same transaction. If the change fails, nothing is sent; if it succeeds, nothing is lost.
  2. Each recipient gets an in-app notice (the bell, refreshed every minute) and a queued email.
  3. Who is told: submitted → the project's QE Leads; approved or returned → the author and submitter; project profile published → its Estimators and QE Leads; global profile → every QE Lead and Admin. Never the person who acted.
  4. A separate worker process picks up due emails. Several workers can run; each email is claimed by one only.
  5. A failed email is retried after 1, 2, 4, 8, 16, then 30 minutes. After 6 attempts it is marked failed.
  6. Emails are plain text plus simple HTML in the recipient's language, with no tracking or remote images.

Operations

Engine versions and stored results

When a formula or default changes, saved estimates never change silently.

What happens

  1. Every saved version keeps the result computed at save time, stamped with its engine version.
  2. A version from an older engine shows "Computed with engine x.y", and the history shows a small badge.
  3. Recompute as new draft starts a draft from that version with the current engine. The comparison then opens, so you see what the engine change did. The old version is unchanged.
  4. Approved versions are never changed, whatever the engine version.
  5. Older stored data is upgraded when read, never rewritten in place. Drafts are recomputed on every autosave, so they are never flagged.

Operations

Admin and audit log

Admins see who uses the app and can switch people off. QE Leads and Admins can see who did what, and when.

What happens

  1. Users (Admins): everyone who has signed in, with project roles and last sign-in.
  2. The Admin role itself is managed in Keycloak, not in the app, so the screen shows it read-only.
  3. An Admin can deactivate a user, who is refused on their next request. Admins cannot deactivate themselves.
  4. Audit log: newest first, filtered by project, record type, action, person and dates. A project's QE Leads see that project; Admins see everything, including global events.
  5. Audit entries never hold estimate inputs, tokens or personal data.

Operations

Languages

The whole app works in English and Vietnamese.

  1. Every screen, email and export label exists in both languages; a test fails if a key is missing in either.
  2. Your language is part of your profile and of the page address, and you can switch it at any time.
  3. Numbers are formatted the same way as the original prototype, so figures match it exactly.
  4. Vietnamese text goes through a reviewer round trip before release.
Proposed

AI assistant through MCP Proposed · not built

Filling in many inputs and judging 142 assumptions is hard. The proposal lets a Quality Engineer give a requirements document to an AI assistant, which proposes the inputs, explains every value, and saves a version only after an explicit yes. An MCP server gives the assistant access to SIT Sizing through the existing API.

This feature is not in the solution design. It is described in its own design spec and ADR-0016 on the feature/mcp-server branch, and is waiting for security review before any build.

How it would work

  1. The QE connects their assistant (Claude Code, Codex and others) to one hosted MCP server and signs in through Keycloak as themselves.
  2. They give it a BRD or FSD. The document stays in the chat; only counts, values and short notes reach the app.
  3. The assistant reads the input and assumption descriptions, proposes values and asks about open questions.
  4. It calls preview: the engine computes the result without saving. The assistant never does the arithmetic itself.
  5. It shows the inputs and result. Only after the user says yes does it create an estimate, update the draft or save a version. Submitting is a separate yes.
  6. Every write runs as the signed-in user, under the same permissions, edit lock, rate limit and audit trail as the web app. It never approves, returns or deletes.
