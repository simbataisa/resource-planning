SIT Sizing Model

Estimate SIT test cases, effort and FTE for a Biz Case or QBR. Start rough from feature sizes, refine with FSD counts, and see which assumptions move the number.

Planning range only. Defaults are uncalibrated heuristics until your team replaces them with actuals. Confirm FTE and timelines with the accountable delivery owner. The example scope below is synthetic.

For the QE team

How to use this tool

Read once, then keep the worked example open while you enter a real project
  1. Pick the mode. No FSD yet: use Rough scope. FSD available: use Detailed scope. Both are always calculated, so the cards and the gap table compare them.
  2. Rough scope. List the features or epics. For each, choose the type (Application, Data platform or AI product), T-shirt size and complexity, and tick Perf-critical when it must meet performance targets. Tick the channels in scope and set roles, languages and variants.
  3. Detailed scope. Work through the nine numbered sections: application drivers, fields and API payloads, roles and rules, channels, data platform, AI product and performance testing. Leave a section at 0 when the change has no such requirements. Each header shows what the section adds up to; Derived drivers shows how every calculated row is built, and the Complexity guide explains Simple, Medium and Complex.
  4. Window, team and environment. SIT weeks, team mix, environment availability, regression automation, AI-assisted test design, AI evaluation runs and SMEs for labelling. Read the Calendar check there: batch windows, labelling lead time or performance environment slots can limit the plan more than FTE.
  5. Shift-left evidence. Enter gate results from the delivery team's pipelines: backend, frontend and mobile L1 tests, data pipeline and contract tests, AI evaluation in CI and reused golden sets, performance smoke tests, APM and reused scripts. Use expected values for a Biz Case and actual values before SIT starts.
  6. Read the result. The four cards show rough and detailed FTE as ranges, the gap between them and how many assumptions are still uncalibrated. The total combines SIT, data, AI and performance testing. Never quote the single figure without its range.
  7. Export. Copy the QBR summary for the deck and export the profile JSON with the project, so the estimate can be reproduced and calibrated later.

Worked example: how the current detailed estimate is built

This trace updates as you change inputs. Follow it from scope to FTE to check the arithmetic.

    How to read the output
    • Range, not a point. Rough is ±40% and detailed ±15% by default; the cone of uncertainty suggests wider bands early on. Quote the range in a Biz Case and the mid value only with the range beside it.
    • Gap table. Shows which drivers explain the difference between rough and detailed, including data, AI and performance rows. A big gap on one driver usually means the T-shirt proxies need calibrating for your product.
    • Sensitivity. The top rows move the estimate most, so calibrate those assumptions first.
    • Shift-left credit. The difference between "No gates" and "All gates met" is the cost of not shifting left: a Biz Case argument for the L1 gates.
    • Calendar check. When batch windows, SME labelling or performance environment slots do not fit the window, adding FTE will not help; start earlier or extend the window.
    • Governance. The FTE and timeline are planning figures. Confirm them with the accountable delivery owner before they go into a commitment.
    Calibration routine after each SIT cycle
    • Count the SIT cases actually run per driver and compare them with the derived rows. Adjust cases per driver until the model lands within range.
    • Measure minutes per case from the test management tool, separately for functional, validation and mobile cases.
    • Take the retest rate from the defect tool: retests ÷ cases run.
    • Take productive hours per day from timesheets.
    • Count request and response fields in one OpenAPI spec to calibrate the per-endpoint field defaults.
    • Data platform: time one load cycle end to end, including data preparation and environment refresh.
    • AI product: time the labelling of 50 samples and one evaluation run with human review.
    • Performance testing: time one script build per complexity and one full test-and-tune cycle.
    • Change the values under Assumptions, name the profile, export it and store it with the project. The next estimate starts from calibrated values.
    Frequently asked questions
    Why 6 productive hours per day, not 8?
    Stand-ups, defect triage, reporting and context switching take about 2 hours of every day. Environment waits are counted separately through the environment factor. Measure it from timesheets and change it under Capacity.
    How does Simple / Medium / Complex change the number?
    It sets both the cases per item and the execution minutes per case (10 / 20 / 40), so one complex API costs roughly 7–8 times a simple one. The Complexity guide (section 9 of the Detailed scope tab) explains how to classify each driver.
    How many validation cases if the gate is missed?
    Every field is tested with the full field-type matrix, about 12 cases per field per layer for a typical mix. At 50–99% coverage half of them come back into SIT. The derived rows show the exact calculation for the current evidence.
    Why is backend validation not covered by the frontend?
    Anyone can call the API directly and skip the UI, and API request fields include fields no screen shows. Backend validation uses the API request fields plus API-only cases such as unknown fields and oversized payloads.
    Why does mutation testing not count as SIT work?
    It is automated and owned by the delivery team. It only decides how much logic testing SIT must repeat: below the gate, business-rule cases and the retest rate go up.
    Why are iOS and Android not a full copy of the web cases?
    Mobile channels re-run a share of the web screen and journey cases (60% by default for native apps), add mobile-only cases such as interrupts and offline, and multiply by the device matrix. A full copy would overstate the effort.
    How are data platforms and AI products estimated?
    Mark the features as Data platform or AI product in Rough scope, and fill the Data platform and AI product sections in Detailed scope. Data platforms are sized by feeds, pipelines, tables, mapped columns, data quality rules and reports, with load cycles bound to batch windows. AI products are sized by labelled evaluation samples, human review per evaluation run and analysis, because their outputs are not deterministic. The calendar check warns when batch windows or labelling lead time, not FTE, limit the plan.
    How is performance testing estimated?
    Mark features as performance-critical in Rough scope, or list performance scenarios in section 7 of Detailed scope. Effort comes from scripting each scenario, the workload model, test data at volume, environment and monitoring, runs per test type and test-and-tune cycles, analysis and reporting. It is added to the combined QE total.
    Can I trust the defaults?
    Not yet. Every default is a heuristic and is labelled uncalibrated until your team replaces it with a measured value. The Standards and rationale section explains where each one comes from.

    1. Rough and detailed use the same formula. Rough fills the driver counts from feature size proxies and uses the longer design time per case, because there is no FSD to design from.
    2. Field validation is credited by coverage. At 100% the team proved it in L1/L2, so SIT runs one sample per screen (frontend) or per API (backend). At 50–99% half the field-type matrix comes back into SIT; below 50% all of it does, about 12 cases per field per layer for a typical mix. Backend validation is not covered by the frontend: it uses the API request fields, which include fields no screen shows, plus API-only cases such as unknown fields and oversized payloads. Mapping is sized by response and payload fields. Validation and mapping cases use their own lighter effort rates and one full pass, because they are templated and data-driven.
    3. A mutation score below the gate means logic defects reach SIT. Business-rule cases go up and the retest rate rises.
    4. Roles use a role × guarded-action matrix with risk-based sampling, never roles × every case. Guarded actions are the protected actions outside workflows plus the role-gated workflow transitions. Each approval workflow adds segregation-of-duties cases.
    5. Business rules split into critical and standard. Critical rules always run the full decision table in SIT. Standard rules are credited by business rule unit tests: one wiring case each when proven, half the table at 50–99%, the full table below 50%. Rules that vary by product, segment or currency are sampled pairwise.
    6. A second web stack or an extra language adds a sampled share of screen and journey cases. Native iOS and Android channels re-run a share of the web cases, add mobile-only cases, multiply by the device and OS matrix and add release cases; they run 1.3× slower. Accessibility adds WCAG cases per screen and channel. Environment availability stretches execution time. Regression automation shrinks only the regression pass; building and maintaining that automation is not counted here.
    7. Data platforms are sized by feeds, pipelines, tables, mapped columns, data quality rules and reports. Data tests are cheap SQL comparisons, but each load cycle is bound to a batch window, so the calendar check compares load cycles with the SIT window. Pipeline tests (dbt, Great Expectations) and data contract tests reduce what SIT repeats.
    8. AI products are not sized as pass/fail cases, because their outputs are not deterministic. They are sized by labelled evaluation samples, a human review of part of the outputs on every evaluation run, and analysis time. Labelling shared with business SMEs is shown in the calendar check, not in QE FTE.
    9. Performance testing is sized by scripted scenarios, runs per test type and test-and-tune cycles, plus workload modelling, test data at volume, environment and monitoring, analysis and reporting. It is part of the combined QE total. Performance smoke tests in CI, APM / OpenTelemetry and reused scripts reduce the effort.
    10. Mutation testing itself is never counted as SIT work. It is automated and owned by the delivery team; it only changes how much SIT has to repeat.

    Basis

    Standards and rationale

    Defaults are heuristics

    No global standard prescribes numbers such as cases per API or minutes per case. Standards define the methods; the numbers come from your own history. This model follows recognised methods and labels every number as a heuristic until a team calibrates it.

    Techniques and references the model relies on

    Part of the modelStandard or referenceWhat it contributes
    Cases per driverISO/IEC/IEEE 29119-4:2021 test design techniques 1Equivalence partitioning, boundary value analysis, decision table testing, state transition testing and combinatorial techniques. The per-driver defaults approximate the smallest case set these techniques produce.
    Overall approachISTQB Foundation 4.0 estimation techniques 2Four recognised methods: ratio-based, extrapolation, Wideband Delphi and three-point. This model is ratio-based; the other three are how you calibrate it.
    Effort structureTMap Test Point Analysis (TPA) 3Size × environment factor × productivity factor, plus an allowance for planning and control (about 10%). The capacity factors (0.7–1.2×) and the 15% overhead follow the same shape.
    Uncertainty rangesCone of Uncertainty, Boehm and McConnell 4Estimate error narrows by stage: 0.25×–4× at initial concept, 0.5×–2× at approved product definition, 0.67×–1.5× at requirements complete.
    Role samplingNIST combinatorial testing research, Kuhn et al. 5Most failures are triggered by one or two interacting factors, which justifies sampling the role × action matrix. NIST also warns that pairs alone are not always enough.
    Cross-checkCapers Jones rule of thumb 6Test cases ≈ function points1.2. Needs an IFPUG or COSMIC function point count. Seen in secondary sources; check the original text before citing.
    Performance testingISO/IEC 25010 performance efficiency; ISTQB Performance Testing syllabusTime behaviour, resource use and capacity as quality characteristics; load, stress, soak, spike and scalability test types and the workload model.

    How to calibrate, using the ISTQB techniques

    1. Ratio-based: run this model on one or two completed projects and compare it with their actual cases and hours. Adjust cases per driver until it lands within range.
    2. Extrapolation: after the first SIT cycle, replace execution minutes per case, retest rate and productive hours with what the team measured.
    3. Three-point: where there is no data yet, ask three senior testers for optimistic (a), most likely (m) and pessimistic (b) minutes per case and use E = (a + 4m + b) ÷ 6.
    4. Wideband Delphi: agree cases per driver across QE leads in short rounds, then export the result as the shared calibration profile.

    Wording for a Biz Case or QBR

    The case-count method follows ISO/IEC/IEEE 29119-4 test design techniques and ISTQB ratio-based estimation. The effort structure is modelled on TMap Test Point Analysis, and the ranges follow the cone of uncertainty. The numeric defaults are uncalibrated heuristics and will be replaced with actuals after the first SIT cycle.
